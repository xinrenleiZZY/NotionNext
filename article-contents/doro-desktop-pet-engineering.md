# 一只桌面宠物，是怎么被我做成一套「系统」的

> 起初只是想让她在桌面上动一动。后来发现，让她「活得像个系统」，比让她可爱难十倍。

`yours_doro_baby` 是我最近做得最投入的一个项目：一只住在 Windows 桌面上的 doro，会自己换动作、会跟你聊天、能修仙、每秒产金币，还能和局域网里的朋友加好友、上排行榜。

它表面上是「一个小玩具」，翻开代码却是一个完整的桌面应用工程：Electron 主进程 + 渲染层、295 个动作素材、版本化的存档、AI 意图校验、Docker 服务端、自动更新。

这篇不复述功能列表（仓库 README 里有），只讲**把它做成系统时踩过的坑和定下的规矩**。

## 一、先定进程边界，再谈功能

Electron 应用最常见的翻车方式，是把所有逻辑都塞进渲染进程：窗口里跑 Node、随意读文件、密钥明文躺在 localStorage。

doro 的边界从第一行代码就定死了：

```
main.js              主进程：窗口、托盘、存档、日志、IPC
preload.js           唯一桥接层（contextIsolation）
renderer/            纯界面：动画、交互、面板
lib/                 可被主进程与测试共用的纯逻辑
```

规矩有三条：

1. **渲染层没有 Node**：`contextIsolation: true`，`nodeIntegration: false`，需要的能力全部由 `preload.js` 白名单暴露。
2. **敏感操作只在主进程**：存档读写、AI 密钥加解密、取题判卷、商城交易校验，渲染层只能「请求」，不能「执行」。
3. **纯函数单独抽出来**：`renderer/game.js`、`renderer/cultivation.js` 里的经济与修炼逻辑不依赖 DOM，可以直接在 Node 里跑单测。

第三条带来的收益在后面会反复出现：**你能用 `node tools/test-game.js` 验证「喂饭 20 金币 +30 饱食」这种规则，而不用真的打开宠物点一百次。**

## 二、素材流水线：246MB → 49MB

桌宠最直观的「好看」，其实是素材工程的胜利。原始素材是 295 个白底 GIF，合计约 246MB，直接丢到桌面上会带一个白框。

我把整个处理做成了可重复的流水线：

```powershell
npm run assets:library   # 按命名表重命名源文件，生成动作清单
npm run assets           # GIF -> 透明 WebP + assets/actions.json
npm run assets:thumbs    # 生成动作库缩略图
```

`tools/prepare_assets.py` 里做了五件事，每一件都是被坑出来的：

| 步骤 | 做法 | 为什么 |
| --- | --- | --- |
| 缩尺寸 | 每帧最长边 300px，WebP 质量 70 | 295 个动作最终约 **49MB**，再大安装包就难受了 |
| 去白底 | 从画布四边做**洪水填充**，只删与边缘连通的白色 | 直接按「白色」抠会把 doro 身上的白毛也抠掉 |
| 羽化 | 对 alpha 做轻微羽化 | 不羽化边缘全是锯齿，放大到 150% 很明显 |
| 并集裁边 | 按所有帧并集统一裁切 | 否则不同动作里的 doro 大小不一，切换动作会「跳」 |
| 托盘图标 | 用待机帧生成 | 少一张额外素材，视觉也统一 |

这套脚本还会自动寻找 `py -3` / `python` / `python3`，也支持用 `DORO_PYTHON` 指定解释器——因为在 Windows 上「找不到 Python」的概率，比脚本本身出错高得多。

## 三、存档：先想清楚「坏档怎么办」

游戏化的桌宠，存档就是生命线。而存档最难的从来不是「写」，是**「写坏了怎么恢复」**。

doro 的存档策略是四层防护：

1. **白名单 + 夹取**：`lib/save-schema.js` 定义每个字段的类型与范围，读档时逐字段校验，越界的直接夹回合法区间。
2. **原子写入**：先写临时文件，再重命名覆盖，避免写到一半断电留下半个 JSON。
3. **双保险落盘**：操作后防抖存档 + 15 秒兜底自动存档。
4. **迁移先备份**：存档已经迭代到 **v30**，每次版本迁移前先把旧档备份到 `save-backups/`，迁移失败还能退回去。

这套东西看起来「过度设计」，直到你收到一个反馈：用户用任务管理器强杀进程，再打开发现金币回到了三小时前。防抖解决高频写入，原子写解决半截文件，版本备份解决「改了 schema 之后老用户进不去」。

**结论：凡是会被用户长期持有的数据，都要按「它一定会坏一次」来设计。**

## 四、AI 聊天：让模型「说话」，不让它「动手」

doro 的 AI 陪伴接的是 OpenAI-compatible 接口（DeepSeek / OpenAI / Ollama 都行）。这里有两个决定，我认为做对了：

**第一，密钥不进渲染层。** API Key 由主进程通过 Electron `safeStorage` 加密后存本地，渲染进程只拿到「已配置/未配置」的状态。会话记录单独存 `ai-history.json`，最近 30 轮，可一键清空。

**第二，模型输出必须经过意图校验。** 这是我认为最值得写进任何 AI 桌面应用的一条：

> 模型可以决定「doro 现在该开心还是该困了」，但不能决定「打开哪个程序、读什么文件」。

实现上，模型返回的是一段受约束的结构：情绪、手势、台词。主进程只把这些映射到本地动作库与气泡，**模型没有直接操作电脑的能力**。这让「AI 陪伴」从安全角度变成了一个可交付的产品，而不是一个需要用户赌运气的实验。

顺带一个工程细节：聊天只携带宠物状态、时间和最近对话，不默认读屏幕、键盘、剪贴板。少拿数据，就少一半事故。

## 五、服务端：能 Docker 的，绝不手搓

桌宠也需要服务端，但我给自己定了条线：**服务端只做「多设备共享」的部分，其余全部本地。**

于是有了三个 Docker 服务：

| 服务 | 端口 | 职责 |
| --- | --- | --- |
| `social-server` | 9500 | 好友、私聊、50 人群聊、排行榜、商城权益 |
| 更新源 | 9400 | Nginx 静态源 + `latest.yml`，`electron-updater` 拉取 |
| 商城目录 | 随 social-server | 商品/价格/加成改动不重新打包客户端 |

```powershell
docker compose -f social-server/docker-compose.yml up -d --build
docker compose -f update-server/docker-compose.yml up -d --build
```

这条线带来的最大好处不是「架构好看」，而是**运营改动不需要发版**：改价格、上下架商品、调加成，改 JSON 文件即可，服务端按更新时间重新加载，客户端拉缓存。

金币、心情、等级、动作进度这些「只属于这个人的东西」依然全部留在本机——**不该同步的绝不为了「云」而云。**

## 六、测试：没有测试的游戏逻辑，一定是玄学

一个桌宠要测什么？我最后拆成了两类：

- **单元测试**（`node tools/test-game.js` 等）：经济、题库判卷、存档 schema、商城目录、社交服务。因为它们都是纯函数或纯数据，跑起来是毫秒级。
- **冒烟测试**（`npm run test:smoke`）：启动一个隐藏的 Electron 窗口，验证界面能起来、关键 IPC 通、动作资源能加载。

再配一个 `npm run perf`：实测冷启动、帧率、内存，输出 `_perf-report.json`。桌宠这种「常驻后台」的应用，内存和帧率就是体感本身，不能靠肉眼猜。

顺便记一个真实的坑：**冒烟测试在没有图形会话的环境里会崩**（`0xC0000005`），所以 CI 必须用 Windows runner 或虚拟显示。这类「本地能过、CI 就崩」的问题，最好在流水线里就标记清楚，而不是等到某天突然红了才查。

## 七、三个真实踩坑

**1. Electron 沙箱读不到 `electron/dist`。**

在 `E:\` 这类数据盘上，目录没有给 `ALL APPLICATION PACKAGES` 读权限，Electron 沙箱检查直接拒绝启动。解决办法是给依赖目录补一次只读 ACL：

```powershell
icacls ".\node_modules\electron\dist" /grant "*S-1-15-2-1:(OI)(CI)(RX)" /T /C /Q
```

**2. 点击穿透不能靠「系统转发」。**

透明无边框窗口想「不挡鼠标」，最直觉的做法是让系统把点击传下去，但实际体验会很「粘」。doro 最后用的是**主进程轮询光标位置**做命中判定：只有宠物本体、金币胶囊、账本面板、右键菜单响应，其余透明区域直接落到桌面。看起来土，但稳。

**3. 安装包大小会反向影响体验判断。**

Electron 44 基线 + 49MB 动作资源，安装包约 **158MB**。用户不会心疼硬盘，但会心疼「下载等了很久」。所以素材压缩、动作按需缩略图、更新只下差异，这些不是优化项，是产品决策。

## 八、把玩具当系统做，才是最好的练习

回头看，这个项目真正让我长本事的，不是「Electron 怎么写」，而是这些：

1. **进程边界**：什么该在主进程、什么该在渲染层，一次定清楚，后面少吵很多架。
2. **素材也是工程**：可重复的脚本 > 手工修图，295 个动作靠手是不可能维护的。
3. **数据要按「会坏」设计**：白名单、原子写、迁移备份，一个都不能省。
4. **AI 要给边界**：让模型表达，不让模型执行。
5. **能 Docker 的服务端才叫服务端**：一行 `docker compose up` 起得来，才敢说交付。

一只桌宠当然不需要这么「重」。但正因为它是玩具，才适合拿它练这些真正在业务系统里才用得上的功夫——**反正坏了也不背 KPI，正好把该踩的坑都踩一遍。**
